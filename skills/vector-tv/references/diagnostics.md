# Диагностика телевизора в сети — без правок на устройстве

Когда ТВ «тормозит», «обновляется по 15 минут» или пропадает из сети, начинать не с
телевизора, а с сети: ADB на Tizen/webOS нет, а половина причин видна снаружи — по портам,
часам и отклику.

## Что снять и чем

Подробности по конкретной сети — ниже (замер 01.11.2026), общая схема такая:

1. **Кто есть в сети.** `ping`-sweep подсети + `ip neigh` + SSDP `M-SEARCH` на 239.255.255.250:1900 —
   SSDP отдаёт `SERVER` и `LOCATION`, по ним видно бренд и модель без логина:
   LG отдаёт `WebOS/1.5 ... webOSTV/1.0` и `friendlyName` в описании, Samsung — `SHP, UPnP/1.0, Samsung UPnP SDK/1.0`.
2. **Порт/линк на промежуточном железе.** Если ТВ за мостом/удлинителем — смотреть линк его
   Ethernet-порта и параметры радиоаплинка (RSSI, rate, режим). Keenetic: `/rci/show/interface`.
3. **Порты самого ТВ.** Набор открытых портов сразу говорит о поколении платформы.
4. **Часы телевизора.** `Date` из ответа на `http://IP/`: у Samsung в стендбае/без NTP это
   `1970-01-01` + время работы, то есть **uptime**, а не дата.
5. **Отклик — только TCP, не ICMP.** Телевизоры душат ICMP, а ноутбук с включённым
   Wi-Fi power save даёт 20–70 % «потерь» на ровном месте — цифры ICMP ничего не доказывают.

## Keenetic (мост/роутер) по RCI

Старые прошивки не имеют веб-API для скриптов, но понимают Basic auth на `/rci/`:

```bash
umask 077 && printf 'machine 192.168.1.70\n  login admin\n  password ***\n' > ~/.config/keenetic.netrc
curl -sS --netrc-file ~/.config/keenetic.netrc http://192.168.1.70/rci/show/version
curl -sS --netrc-file ~/.config/keenetic.netrc http://192.168.1.70/rci/show/interface
curl -sS --netrc-file ~/.config/keenetic.netrc http://192.168.1.70/rci/show/system
```

Что смотреть в `show/interface`: `FastEthernet0.link` (кабель), `WifiMaster0/WifiStation0`
(`rssi`, `rate`, `bw`, `mcs`, `mode` — аплинк моста), `Home` (bridge, его адрес и MAC).
Нет `/rci/show/ip/hotspot` и `/rci/show/associations` → 404: это старая ветка (2.15), клиенты
за мостом видны только через главный роутер.

## Ловушки, которые сбивают диагноз

- **MAC клиентов за мостом.** Если в ARP у ТВ и у моста одинаковый MAC, это не глюк: мост ходит
  в сеть своим MAC (MAC-NAT), и по ARP нельзя отличить устройства за ним — только по портам.
- **ICMP «потери».** 70 % потерь ICMP и при этом 10/10 TCP по 6 мс — норма для телевизора в
  стендбае/с приоритизацией ICMP. Выводы делать по TCP-коннекту, а не по `ping`.
- **Power save на ноутбуке.** `iw dev <if> get power_save` → `on` завышает задержку и «потери» до
  всех хостов сразу (в замере до шлюза было 170 мс при сигнале −58 дБм). Выключение требует root:
  `sudo iw dev <if> set power_save off`. Без root — сравнивать хосты между собой, а не абсолютные мс.
- **Стендбай Samsung.** В глубоком сне Ethernet PHY гаснет: порт моста уходит в `link=down`, ARP
  становится `FAILED`. Это не поломка кабеля — проверять при включённом ТВ.
- **Часы 1970 — не «сбитая дата», а отсутствие NTP.** TLS к серверам с такой датой не проходит:
  «сертификат ещё не действителен», обновления и сервисы уходят в бесконечные ретраи.

## Что говорит набор портов (Samsung)

| Порты | Что это |
|---|---|
| 80, 443 | встроенный веб-сервер, `/api/v2/` → 401 требует токен |
| 55000 | legacy-пульт (Orsay, 2011–2014); на живом ТВ принимает медленно — 458 мс против 6 мс у 7676 |
| 7676 | Samsung Media Player (DLNA), описание — 401 Unauthorised |
| 9090 | второй канал пульта, отвечает `application/octet-stream` |
| 8001, 8002 закрыты | нет современного REST/websocket → платформа старая или API выключен |
| DIAL не отвечает | управление приложениями снаружи недоступно |

Модель и прошивку без токена не получить. Единственный путь — `/api/v2/` с сопряжением:
на экране ТВ появится запрос «Разрешить доступ?», его нажимает владелец. Это единственное
действие, которое требует его рук; без него остаётся пульт: Настройки → Поддержка → Об этом ТВ.

## Замер 01.11.2026 (сеть владельца)

```
роутер Keenetic       192.168.1.1    WAN 92.38.239.36, аптайм 82 дня, ошибок нет
LG UN74006LA          192.168.1.71   напрямую; 3000/3001/1964 открыты; TCP 5,7 мс медиана
Keenetic Start        192.168.1.70   2.15.C.4.0-1, MIPS, аптайм 14,4 сут; MAC моста 52:ff:20:0d:f8:f5
  аплинк             2,4 ГГц, 802.11n, 40 МГц, MCS15, 270–300 Мбит, RSSI −39 дБм, стабилен
  FastEthernet0      при выключенном ТВ link=down, при включённом — link=up
Samsung               192.168.1.61   часы 1970-01-01 + uptime, TLS только ≤1.1, порты 80/443/55000/7676/9090
```

Наблюдения: путь до Samsung по TCP 6–9 мс (сеть в порядке), 55000 — 458 мс (служба занята),
ICMP 23–71 % «потерь» (душится), uptime после включения растёт линейно — за 4 минуты
наблюдения перезагрузок не было.

Что осталось непроверенным: модель и версия прошивки, журнал обновлений, реальная причина
«15 минут» (гипотеза — отсутствие NTP и TLS 1.0 ломают серверные вызовы), поведение при
длительном простое, есть ли на ТВ обновление в очереди.
